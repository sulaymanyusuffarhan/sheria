# LSMS — proposed logical data model

**Draft for review** · [Architecture proposal](proposal.md) · [Workflows](workflows.md)

This is a logical schema, not SQL, a migration or a deployed database. Physical types, nullability, index sizes, encryption profiles, classification codes and retention durations need the signed SRS/data dictionary and testing on the agreed database engines.

## 1. Relationship overview

```text
Directorate 1 ─── * Department 1 ─── * LegalMatter
Department  * ─── * Person (dated memberships; offices separately scoped)
Person 1 ─── * UserAccount * ─── * Role * ─── * Permission (scoped role grants)

LegalMatter 1 ─── 0..1 LegalRequest (staff intake, if present)
LegalMatter 1 ─── 0..1 Specialist record (exclusive per matter):
   Contract     1 ─── * ContractVersion 1 ─── * ContractChecklist 1 ─── * ChecklistResponse
   Litigation   1 ─── * CourtHearing / CaseParty / Order / Outcome
   LegalOpinion 1 ─── * LegalOpinionVersion
   IP record    1 ─── * Licence 1 ─── * RightsGrant
   Obligation   1 ─── * Review / CorrectiveAction / Evidence
LegalMatter 1 ─── * Assignment / Task / WorkflowInstance / AccessGrant
WorkflowInstance 1 ─── * WorkflowEvent / ApprovalRound
ApprovalRound 1 ─── * ApprovalDecision; binds an immutable typed review package

Matter or authorised repository collection 1 ─── * LegalDocument
LegalDocument 1 ─── * DocumentVersion 1 ─── * Explicit Release or Evidence Link
UserAccount 1 ─── * Notification / AuditLog (system actors separately identified)
```

Staff submissions and specialist records share a `legal_matter` anchor without copying the request's description or status into every register. A direct legal registration may have no staff request. Keep separate but coordinated intake and specialist workflow lanes. If one submission uncovers multiple matters, create separate linked matters with independently checked access; a link is not a permission. The baseline allows at most one specialist kind per anchor (validate using the anchor's typed kind/key plus subtype FK and uniqueness). Confirm bundling rules with DLS before design sign-off.

## 2. Identity, scope and common matter records

Notation: **FK** is a foreign key; **UQ** is a unique constraint. Use immutable opaque IDs for records, distinct from human references. All relations below use referential constraints unless identified as an immutable historical snapshot. FK columns that drive joins and deletes are indexed. Dated revocation is preferable to deleting an actor or assignment.

| Entity or group | Key attributes and relationships |
| --- | --- |
| `directorates`, `departments`, `offices`, `department_offices` | Stable codes and active periods. A department belongs to one directorate at a time; an authorised regional office is related to its serviced department(s). Track code/structure changes; preserve submission-time organisation in reports. |
| `people`, `users`, `identity_links`, `department_memberships` | Link credentials/account status to a verified person; prefer UQ `(issuer, subject)` for federated identity. Each membership links a person to a department and optional valid office, with effective dates and provenance. Keep optional employee number and contact info restricted, off URLs and audit diffs. Technical vs ordinary employee accounts are distinct; all map to the same verified person when applicable. |
| `roles`, `permissions`, `role_permissions`, `user_role_grants` | Stable role/action codes, role–permission join, grant with account, optional department/office or approved portfolio/queue via FK scope, purpose, authoriser and validity; deny grants with mismatched scope. `approval_delegations` records acting capacity, scope, evidence, issuer and validity. `matter_access_grants` links user to matter with action boundaries, clearance, reason, expiry and revocation. Neither bypasses mandatory restrictions. |
| `legal_matters`, `matter_links` | Matter kind, originating department/office, responsible scope, classification, priority and timestamps; one scope root for policy. Directed typed links between existing matters, UQ `(from_matter, to_matter, relation)` and no self-links. Separate originating scope from any later transfer of responsibility. |
| `legal_requests`, `request_submissions` | `legal_requests.matter_id` is UQ FK; request reference UQ once submitted, category, requester and submission time. Immutable submitted iterations have title, issue/description, background, contact and requester/department/directorate snapshot, optional employee ID only if needed, desired date, requested priority, declaration version/acknowledgment and clean attachment links. Supplemental answers preserve prior submissions. Staff profile changes do not alter those snapshots. |
| `legal_assignments`, `active_assignments` | Matter, purpose/queue, assigned and assigning users, effective start/end, due date, instructions/priority and reason. One active primary assignee per matter and assignment purpose through UQ slot `(matter, purpose)` referencing an eligible assignment; history is preserved on reassignment. |
| `legal_request_comments`, `request_information_rounds` | Matter/request, author, timestamp and protected body. Keep internal notes separate from staff correspondence in permitted query paths. Staff-visible messages have explicit publication and audience, not classification inferred from author. Information rounds track question/reply, due date, saved review step, verification and closure. |
| `reference_counters`, `idempotency_records` | UQ `(numbering_namespace, EAT_year)`; lock counter row per namespace/year and allocate in the same transaction as registration. UQ reference and sequence per namespace/year. Retry keys scoped to actor/command, with request digest and response pointer; never repeat an action silently on payload mismatch. |

Request and contract categories are managed code lists with English/Kiswahili labels and active dates. Baseline request codes cover contract review, legal opinion/advice, litigation, employment/labour, IP, broadcasting/media rights, copyright infringement, defamation, regulatory compliance, MoU and other. Contract categories cover procurement, content acquisition, sponsorship, advertising, ICT/digital, public–private partnership, lease, consultancy, MoU, employment-related, broadcasting rights and other. Use stable codes, not translated text, for rules and reporting. A registration returns the committed reference (e.g. `TBC/DLS/2026/0001` for a request). Year is the institutional EAT calendar at registration; sequence is at least four digits, not capped at 9,999. Do not recycle a committed reference after rejection, archival or migration.

## 3. Workflow and decisions

| Entity or group | Key attributes and relationships |
| --- | --- |
| `workflow_definitions`, `workflow_versions`, `workflow_states`, `workflow_transitions` | Definitions by lane/kind; immutable published versions; state codes, command, from/to, permission, template/rule requirements and named guard IDs. UQ codes/transition identity per version; transitions FK to states in the same version. Store approved configuration, not arbitrary executable policy. |
| `workflow_instances`, `active_workflow_lanes`, `workflow_events` | Instance links matter, pinned policy version, lane, run, current state, revision, deadline and closure time. UQ active slot `(matter, lane)` holds the live instance, not one DB-specific partial index. Append-only events record actor/role, from/to, previous/current instance revision, reason, occurrence time and related domain event. Staff timelines project only explicitly safe milestones. |
| `approval_rounds`, `approval_decisions` | Round UQ `(instance, round_no)`, submitted by/at, immutable typed package and digest. Append-only decisions FK round and configured gate, UQ one decision per gate per round; effective human actor/person, role/delegation, authenticated intent/MFA evidence marker, timestamp, result and reason. Opening a new round doesn't overwrite a previous decision. Typed packages (request recommendation, contract and opinion) associate exact immutable business and document revisions; the intake lane may mirror a domain decision, not manufacture a second one. |
| `legal_tasks`, `calendar_events`, `working_calendar_versions` | Tasks belong to matters or authorised operational queues; assignee, priority, deadline, state and escalation setting. Events for hearings, meetings, regulatory/assignment deadlines, expiries, renewals or submission due dates, with source link, participants and visibility. Source records own their dates; projected reminders are regenerated on changes. Holiday/SLA calendar version defines schedule and permissible pauses. |

## 4. Contract lifecycle

| Entity or group | Key attributes and relationships |
| --- | --- |
| `contracts`, `contract_versions` | `contracts.matter_id` UQ FK; unique contract reference, category and origin. Version UQ `(contract, version_no)`, title, commercial terms, decimal value/currency, duration, effective/expiry proposals, responsible officer and draft document version. Review binds an exact version and snapshots display values only as needed to preserve historical facts (e.g. department and counterparty names). Executed terms/dates are owned by the execution record, not replaced by working drafts. |
| `contract_parties` | FK contract version, legal capacity, legal name, verified registration, authority/signatory and verified source via evidence. UQ version/party/capacity as appropriate. Avoid exposing a global counterparty index across confidential matters. |
| `checklist_templates`, `checklist_sections`, `checklist_items` | UQ `(document_reference, revision)`; authorised source, owning DLS, classification and ordered structure A and Parts I–XIII. Stable item IDs within immutable template versions; UQ section/item order and code; structured Risk/Approval fields not disguised as Boolean responses. |
| `contract_checklists`, `checklist_responses`, `checklist_response_documents` | FK contract version and template version, kind (pre-clearance or post-execution), round, reviewer, save revision and frozen time. Post-execution instance references execution. UQ `(checklist, item)`; choice Yes/No/N/A or unanswered draft, remarks and last editor. FK invariants: item belongs to pinned template, its section belongs to review phase, and attached clean `document_version` belongs to authorised matter. |
| `contract_risks`, `contract_review_packages`, `contract_approvals`, `contract_conditions` | Risk rows FK pre-clearance checklist (risk class recorded separately from individual likelihood/impact rows). Typed package PK/FK approval round pins contract version, frozen checklist and supporting evidence. `contract_approvals` extends an approval decision via PK/FK for clearance/recommendation attributes. Conditions have responsible person, deadline, evidence and signed verification. A condition check never rewrites a decision or approves the contract. |
| `contract_amendments`, `contract_executions`, `contract_documents`, `contract_monitoring_items` | Amendment/renewal unique per contract sequence with previous/proposed version, rationale and decision trail; execution links the cleared version/decision and evidence of applicable external prerequisites and matching signed counterpart. Record effective/expiry dates, signatory authority, contract manager, formal register entry, post-execution review and original archive. Monitor obligations and renewal milestones as linked tasks; do not overwrite older periods. `contract_documents` binds document versions to authorised contract version and purpose. |

## 6. Documents, evidence, audit and operations

| Entity or group | Key attributes and relationships |
| --- | --- |
| `legal_documents`, `document_collections`, `document_categories`, `document_tags`, `document_tag_links` | Each document belongs to a matter or a governed repository collection, with category, owner/classification and retention rule. Categories include contracts, agreements, MoUs, court documents, judgments, opinions, correspondence, internal memoranda, regulatory, IP, templates and research. Tags never grant access. A cross-matter disclosure needs a separately authorised release/copy, not an unrestricted link to the original. |
| `document_uploads`, `document_versions`, `document_derivatives` | Upload status/quarantine, uploader/date and verified result. UQ `(document, version_no)` and opaque storage object key. Store size, detected media type, digest, encryption key reference, clean verdict/status, provenance and classification; object is outside DB. Approved previews and extraction artifacts inherit access and lifetime. Never release a quarantined file. |
| Version links and `document_releases`, `release_audiences` | `request_documents`, `contract_documents`, `case_documents` and other join tables FK exact document version and parent; no unconstrained `type/id` links for business evidence. Release records bind version, approving decision/authorisation, audience, issue event, expiry/revocation. Staff access requires a current release and matching authorised scope; DLS source access is separate. |
| `retention_schedule_versions`, `legal_holds`, `hold_matter_links`, `hold_document_links`, `disposition_actions` | Versioned rules by classification/category and trigger event, authorised holds across related matters/documents, case IDs and reasons, custody/transfer and two-person disposition with evidence. Holds apply to all affected versions and derivatives. No cascading deletion of evidence or decisions. Retain minimal approved proof of disposition after approved deletion. |
| `notifications`, `notification_preferences`, `outbox_events`, `delivery_attempts`, `scheduled_jobs` | In-app inbox per user with read time; category/channel rules approved by ICT/DLS. Durable events with correlation/causation IDs, retry/lock expiry and UQ dedupe keys on delivery. Payloads use scoped references and minimal template variables; resolve content only after authorisation. |
| `report_runs` | Requested by, report/filters, authorised scope snapshot, timezone, generation time, expiry and private version ID. Verify current scope at execution and retrieval; loss of scope invalidates the generated artifact. |
| `audit_logs`, `system_settings`, `change_requests` | Append-only audit anchored by matter/actor where available; UTC occurrence, action, version, result, before/after metadata or controlled references, source/correlation and protection classification. Partition/archive by approved policy. Settings use typed values and separate secret-store references. Changes track initiation, impact, authorisation, test, delivery and rollback evidence; no access to case material by default. |

## 7. Integrity rules and query design

- **Normalise mutable data; pin evidence deliberately.** Use reusable code tables, FK links, many-to-many joins and explicit versions. Revisions, declarations, decisions and historical snapshots are immutable. Dated changes to people, organisations or references do not rewrite signed snapshots. Use bounded structured payloads only for snapshots, outbox messages and approved config, not to replace legal relations.
- **Time and money:** UTC for instants, date-only for calendar obligations when appropriate, TZ source persisted for imported hearing times, EAT for period/sequence calculations; use exact decimal values plus currency code. Validate due dates, ranges and ordering without assuming a universal statutory deadline. Historical records retain original numbers and provenance separate from LSMS IDs.
- **Atomic safety:** check that review package, decision, assigned reviewer and file versions all belong to the same matter; forbid decision against stale versions or self-approval despite overlapping roles. Cover cross-row invariants with composable FK/unique constraints where possible and transactional service guards for authority and conditions. Use DB insert-only permissions on audit for normal runtime. Suspend disposal during hold/restore reconciliation and disable hard deletes from ordinary UI/APIs; use deactivation, supersession and retention disposition instead.
- **Index for the review queues:** unique reference lookup; composite for owning/originating scope, category, status and date; assignment by officer/end/due date; hearings/expiry/reminders by dated state; unread inbox by user; append-only audit by actor, matter and time. Join policy scope before projecting counts/search text or pagination; invalidate policy-dependent cache when grants or classification change. Benchmark representative regional and confidential workloads with synthetic data.
- **Migration and portability:** regress uniqueness under concurrent submit, sequence year rollover, state transitions, date/collation precision, permission-filtered search and rollback on PostgreSQL and the nominated alternative. Keep a unique source-system/external-ID mapping for idempotent reimports. Reconcile identifiers, owner, classification and hash manifests; quarantine ambiguities for officer review. Never load existing approvals or court outcomes that lack traceable evidence.
